# GStack 技能使用指南

> 基于 [garrytan/gstack](https://github.com/garrytan/gstack) 官方文档编写

## 简介

GStack 是由 Y Combinator CEO Garry Tan 开发的 AI 辅助开发工具集，它将 Claude Code 转换为一个虚拟工程团队。包含 23 个专家角色和 8 个强力工具，所有命令都是斜杠命令（slash commands），全部使用 Markdown 编写，MIT 开源许可。

**核心理念**：Think → Plan → Build → Review → Test → Ship → Reflect

每个技能都会传递信息给下一个技能，形成完整的开发流程闭环。

---

## 技能分类

### 一、思考与规划阶段 (Think & Plan)

#### 1. `/office-hours` - YC Office Hours
**角色**：YC 创业导师
**功能**：
- 通过 6 个强制性问题重新定义你的产品
- 挑战你的框架假设，质疑前提条件
- 生成实现方案替代选项
- 输出设计文档，自动传递给下游技能

**使用场景**：
- 开始任何新功能开发之前
- 需要重新思考产品方向时
- 想要验证想法的可行性时

**示例**：
```
用户: 我想构建一个日历简报应用
Claude: [询问痛点 - 具体例子，而非假设]
用户: 多个 Google 日历，事件信息陈旧，地点错误...
Claude: 我要挑战你的框架。你说"日历简报应用"，但你实际描述的是一个私人参谋 AI...
```

---

#### 2. `/plan-ceo-review` - CEO/创始人审查
**角色**：CEO / 创始人
**功能**：
- 重新思考问题，找到隐藏在需求中的 10 星级产品
- 四种模式：扩展（Expansion）、选择性扩展（Selective Expansion）、保持范围（Hold Scope）、缩减（Reduction）
- 读取 `/office-hours` 生成的设计文档
- 运行 10 个部分的审查

**使用场景**：
- 需要挑战功能范围时
- 想要找到更好的产品方向时
- 在实现前进行战略审查时

---

#### 3. `/plan-eng-review` - 工程经理审查
**角色**：工程经理
**功能**：
- 锁定架构、数据流、图表、边缘情况和测试
- 强制暴露隐藏的假设
- 生成 ASCII 图表（数据流、状态机、错误路径）
- 创建测试矩阵、失败模式、安全考虑

**使用场景**：
- 需要详细的技术规划时
- 架构设计阶段
- 需要识别技术风险时

---

#### 4. `/plan-design-review` - 高级设计师审查
**角色**：高级设计师
**功能**：
- 对每个设计维度评分 0-10
- 解释什么是 10 分的样子
- 编辑计划以达到目标
- AI Slop 检测
- 交互式 - 每个设计选择一个 AskUserQuestion

**使用场景**：
- UI/UX 设计审查
- 视觉设计质量检查
- 交互设计优化

---

#### 5. `/plan-devex-review` - 开发者体验审查
**角色**：开发者体验负责人
**功能**：
- 探索开发者角色画像
- 与竞争对手的 TTHW（Time to Hello World）进行基准测试
- 设计神奇时刻
- 逐步追踪摩擦点
- 三种模式：DX EXPANSION、DX POLISH、DX TRIAGE
- 20-45 个强制性问题

**使用场景**：
- 开发 API、SDK、库或平台时
- 需要优化开发者体验时
- 文档和入门流程设计时

### 二、设计阶段 (Design)

#### 6. `/design-consultation` - 设计咨询
**角色**：设计合作伙伴
**功能**：
- 从零开始构建完整的设计系统
- 研究设计领域
- 提出创意风险方案
- 生成真实的产品模型
- 创建 DESIGN.md 作为项目设计真理来源

**使用场景**：
- 新项目开始时建立设计系统
- 需要完整的品牌指南时
- 创建字体和颜色预览页面时

---

#### 7. `/design-shotgun` - 设计探索
**角色**：设计探索者
**功能**：
- "展示选项" - 生成 4-6 个 AI 模型变体
- 在浏览器中打开比较面板
- 收集反馈并迭代
- 品味记忆学习你喜欢什么
- 重复直到你爱上某个设计，然后交给 `/design-html`

**使用场景**：
- 需要探索多种设计方案时
- 不确定最终设计方向时
- 想要快速生成多个选项时

---

#### 8. `/design-html` - 设计工程师
**角色**：设计工程师
**功能**：
- 将模型转换为可生产的 HTML
- Pretext 计算布局：文本重排、高度调整、布局动态
- 30KB，零依赖
- 检测 React/Svelte/Vue
- 智能路由（落地页 vs 仪表盘 vs 表单）
- 输出可直接发布，而非演示

**使用场景**：
- 将设计稿转换为生产代码时
- 需要高质量的 HTML/CSS 实现时
- 从 `/design-shotgun` 的结果生成代码时

---

#### 9. `/design-review` - 设计师代码审查
**角色**：会写代码的设计师
**功能**：
- 与 `/plan-design-review` 相同的审查
- 然后修复发现的问题
- 原子提交，前后截图对比

**使用场景**：
- 实时站点视觉审查时
- 需要修复视觉问题时
- 设计质量保证时

---

### 三、构建与审查阶段 (Build & Review)

#### 10. `/review` - 工程师代码审查
**角色**：高级工程师
**功能**：
- 发现通过 CI 但在生产环境会爆炸的 bug
- 自动修复明显问题
- 标记完整性缺口
- SQL 安全检查
- LLM 信任边界违规检查
- 条件副作用检查

**使用场景**：
- 合并 PR 前的审查
- 代码质量检查
- 生产环境风险识别

---

#### 11. `/investigate` - 调试器
**角色**：调试专家
**功能**：
- 系统性根因调试
- 铁律：没有调查就没有修复
- 追踪数据流
- 测试假设
- 3 次失败修复后停止

**使用场景**：
- 遇到复杂 bug 时
- 需要系统性调试时
- 性能回归分析时

### 四、测试阶段 (Test)

#### 12. `/qa` - QA 负责人
**角色**：QA 负责人
**功能**：
- 测试应用，发现 bug
- 用原子提交修复它们
- 重新验证
- 为每个修复自动生成回归测试
- 三个层级：Quick（仅关键/高优先级）、Standard（+中等）、Exhaustive（+外观）

**使用场景**：
- 功能完成后测试时
- 需要发现并修复 bug 时
- 发布前质量保证时

---

#### 13. `/qa-only` - QA 报告员
**角色**：QA 报告员
**功能**：
- 与 `/qa` 相同的方法论
- 仅报告，不修改代码
- 纯 bug 报告

**使用场景**：
- 只需要 bug 报告时
- 不希望自动修复时
- 外部 QA 团队审查时

---

#### 14. `/browse` - QA 工程师
**角色**：QA 工程师
**功能**：
- 给代理眼睛 - 真实的 Chromium 浏览器
- 真实点击、真实截图
- ~100ms 每个命令
- `/open-gstack-browser` 启动带侧边栏的 GStack 浏览器
- 反机器人隐身、自动模型路由

**使用场景**：
- 需要测试真实浏览器行为时
- 截图验证时
- 交互测试时

---

#### 15. `/devex-review` - DX 测试员
**角色**：开发者体验测试员
**功能**：
- 实时开发者体验审查
- 实际测试入门流程：导航文档、尝试快速开始流程
- 计时 TTHW
- 截图错误信息
- 与 `/plan-devex-review` 分数对比 - 回旋镖效应

**使用场景**：
- 开发者工具发布前测试时
- 文档质量验证时
- 入门流程优化时

### 五、安全阶段 (Security)

#### 16. `/cso` - 首席安全官
**角色**：首席安全官
**功能**：
- OWASP Top 10 + STRIDE 威胁模型
- 零噪音：17 个误报排除、8/10+ 置信度门控
- 独立发现验证
- 每个发现包含具体的利用场景
- 基础设施优先安全审查：密钥考古、依赖供应链、CI/CD 管道安全、LLM/AI 安全、技能供应链扫描

**使用场景**：
- 安全审查时
- 威胁建模时
- 渗透测试审查时
- 依赖漏洞扫描时

### 九、工具类技能 (Utilities)

#### 24. `/autoplan` - 自动审查管道
**功能**：
- 从磁盘读取完整的 CEO、设计、工程和 DX 审查技能
- 使用 6 个决策原则自动决策顺序运行
- 在最终批准门控处显示品味决策（接近方法、边界范围、法典分歧）
- 一个命令，完全审查的计划输出

**使用场景**：
- 需要完整的审查流程时
- 自动化决策时
- "自动审查"、"自动计划"、"运行所有审查"时

---

#### 25. `/pair-agent` - 多代理协调器
**角色**：多代理协调器
**功能**：
- 与任何 AI 代理共享浏览器
- 一个命令，一个粘贴，已连接
- 适用于 OpenClaw、Hermes、Codex、Cursor 或任何可以 curl 的工具
- 每个代理获得自己的标签页
- 自动启动有头模式以便观看所有内容
- 自动启动 ngrok 隧道用于远程代理
- 作用域令牌、标签页隔离、速率限制、活动归属

**使用场景**：
- 多代理协作时
- 远程代理访问时
- 浏览器共享时

---

#### 26. `/setup-browser-cookies` - 浏览器 Cookie 设置
**功能**：
- 从真实 Chromium 浏览器导入 cookie 到无头浏览会话
- 打开交互式选择器 UI 选择要导入的 cookie 域
- 在 QA 测试认证页面前使用

**使用场景**：
- 测试需要认证的页面时
- 导入登录状态时
- 认证浏览器时

#### 27. `/setup-deploy` - 部署设置

**使用场景**：
- 首次设置部署时

**功能**：

- 捕获每个远程信任策略
- 一个命令从零到"gbrain 正在运行，此代理可以调用它"

**使用场景**：
- 设置 gbrain 时

#### 29. `/careful` - 安全防护
**功能**：
- 破坏性命令的安全防护
- 在 rm -rf、DROP TABLE、force-push、git reset --hard、kubectl delete 等操作前警告
- 用户可以覆盖每个警告

**使用场景**：
- 操作生产环境时
- 调试实时系统时
- 在共享环境中工作时

#### 30. `/freeze` - 冻结编辑范围
**功能**：

**使用场景**：
- 需要限制编辑范围时
- 调试时防止意外修改时
- 模块隔离工作时

---

#### 31. `/guard` - 完全安全模式
**功能**：
- 完全安全模式：破坏性命令警告 + 目录范围编辑
- 结合 `/careful` 和 `/freeze`
- 用于操作生产或调试实时系统时的最大安全性

**使用场景**：
- 操作生产环境时

#### 36. `/scrape` - 网页抓取
**功能**：
- 从网页拉取数据
- 首次调用新意图时通过 $B 原型化流程并返回 JSON
- 后续调用匹配意图时路由到编码的浏览器技能并在 ~200ms 内返回
- 只读 - 对于可变流程（表单填充、点击、提交），使用 `/automate`

**使用场景**：
- 从网页提取数据时
- 抓取内容时
- 只读网页访问时

---

#### 37. `/skillify` - 技能化
**功能**：
- 将最近的 `/scrape` 流程编码为磁盘上的永久浏览器技能
- 未来相同意图的 `/scrape` 调用在 ~200ms 内运行编码脚本，而不是重新驱动页面
- 回溯对话、合成 script.ts + script.test.ts + fixture
- 在临时目录运行测试，提交前询问

**使用场景**：
- 保存抓取流程时
- 创建永久技能时
- 自动化重复任务时

## 完整工作流程示例

### 场景 1：构建新功能

```
1. /office-hours          # 定义产品，挑战假设
2. /plan-ceo-review       # 战略审查，范围挑战
3. /plan-eng-review       # 架构锁定，技术规划
4. [实现代码]
5. /review                # 代码审查，发现 bug
6. /qa https://staging... # QA 测试，修复 bug
7. /ship                  # 创建 PR
8. /land-and-deploy       # 合并并部署
9. /canary                # 监控生产环境
```

### 场景 2：安全审查

```
1. /cso                   # 运行安全审查
2. [修复发现的问题]
3. /review                # 审查修复
4. /ship                  # 发布修复
```

### 场景 3：设计新 UI

```
1. /design-consultation   # 建立设计系统
2. /design-shotgun        # 探索多个选项
3. /design-html           # 实现选定的设计
4. /design-review         # 视觉审查和修复
5. /qa                    # 功能测试
```

## 最佳实践

1. **始终从 `/office-hours` 开始** - 即使你认为自己知道要构建什么，也要让代理挑战你的假设

2. **按顺序使用技能** - 每个技能都设计为从前一个技能的输出中读取

3. **不要跳过审查** - `/review` 和 `/qa` 能发现 CI 无法捕获的生产 bug

4. **使用 `/canary` 监控** - 部署后始终监控生产环境

5. **定期运行 `/retro`** - 每周回顾帮助识别模式和改进机会

6. **信任流程** - GStack 是一个流程，不是工具集合。让它完整运行
